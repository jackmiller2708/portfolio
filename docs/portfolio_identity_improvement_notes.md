# Portfolio Identity Improvement Notes - Personalized Version

Scope: identity layer only.

This intentionally leaves out proof, case studies, lab notes, and sample audit content because those are placeholder sections for later polish.

The focus here is: make the portfolio clearly belong to **Nguyen Ngoc Huy**, also known as **Jack** for English-speaking clients, instead of feeling like an abstract brand called **Frontend Systems**.

---

## 1. Main diagnosis

The current portfolio has a strong technical concept, but the personal identity layer is still too abstract.

Right now, the site feels like it belongs to an entity called **Frontend Systems**. That sounds like a studio, agency, product, or consulting label. The positioning is good, but the person behind the work is under-presented.

For contractor work, especially architecture audits and refactor planning, trust attaches faster to a named person than to a faceless brand.

The fix is not to make the portfolio casual or overly personal. The fix is to make the site feel like it belongs to a real, accountable engineer with:

- a real name
- a practical English nickname
- a real email
- a location
- a narrow technical specialty
- visible contractor boundaries
- a clear working style
- a credible technical personality

The target impression should be:

> This is Nguyen Ngoc Huy, who English-speaking clients can call Jack. He is a Vietnam-based Angular Frontend Systems Engineer who helps teams make complex Angular systems easier to reason about, safer to change, and more maintainable.

## 7. About page rewrite

Current issue:

The About page explains the philosophy, but it does not make the person visible enough.

Recommended About opening:

```md
# About Nguyen Ngoc Huy

I am an Angular Frontend Systems Engineer based in Vietnam. English-speaking teams can call me Jack.

I work with teams whose Angular applications have become difficult to change because state ownership, RxJS flows, service boundaries, data access, and error handling are no longer explicit.

My strongest work is not UI-only implementation. It is making complex frontend systems easier to reason about, safer to modify, and more stable under product pressure.
```

Add this after the opening:

```md
## What I work on

My strongest production work is Angular, especially Angular 12-18 applications, RxJS-heavy systems, frontend architecture, explicit data/error handling, and maintainable TypeScript design.

I also understand React and Next.js, but my contractor positioning is intentionally Angular-first. React/Next.js work should be secondary unless the problem is architecture, frontend quality, refactoring, or a clearly scoped implementation.
```

Add this philosophy block:

```md
## What I protect in frontend systems

Most frontend problems are not framework problems. They are boundary problems: unclear ownership, hidden side effects, scattered state, inconsistent error handling, and code paths that only one person understands.

I care about making those boundaries visible. That can mean clarifying data access, separating orchestration from rendering, naming stream ownership, modeling absence and failure explicitly, or documenting tradeoffs before a refactor turns into a rewrite.
```

Add this working style block:

```md
## How I work

I prefer scoped work with visible deliverables: audits, refactor plans, stabilization sprints, architecture reviews, and decision notes.

I do not optimize for abstract purity. I optimize for the best engineering outcome given the product goal, timeline, budget, team capacity, and long-term maintenance cost.
```

Add this communication block:

```md
## Communication

I work comfortably in Vietnamese and English. For English-speaking clients, Jack is fine.

I work best with direct context: what the product does, where the frontend feels risky, what has already been tried, and what outcome the team needs first.
```
